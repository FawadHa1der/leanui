# Keep compiling Lean; benchmark lean-vir beside it

LeanUI should not move to lean-vir. Add it as one more implementation in the benchmarks, pinned to an exact lean-vir commit and its matching runtime resource, and keep compiled Lean → C → wasm as the production runtime. Running LeanUI's own Bench logic (update, view, diff and command encoding) under lean-vir took **11–55× as long as today's wasm64 build** in Chromium and release Firefox. Pixel kernels took **42–211× as long**, downloads grew about 1.6×, startup slowed about 2×, and the packager rejected the photo editor for seven missing primitives (all timings: CI machine, to be re-measured on the reference Mac). lean-vir does bring two real gains: a build with no Emscripten, Docker or forked runtime, and in-page Safari support. The Safari gain is shrinking, because WebKit's main branch already turns Memory64 on by default. Durability points the same way. Upstream Lean is investing in its LCNF-based C emitter. lean-vir is a five-month-old, single-maintainer proof of concept that depends on Lean's internal IR layout, promises no compatibility across revisions, went through four contract versions in 12 days and had red CI at the commit studied. For lean-vir itself, the durable target is the one it already ships: **wasm32-wasip1, built with wasi-sdk clang and loaded by its own small JS**. A Memory64 port works (an Emscripten prototype needed about 50 changed lines), but it ran 1.1–1.35× slower, was about 10% larger than a same-toolchain wasm32 build, reached about 40% less recursion depth and excludes every Safari and iOS user. It pays off only for heaps above about 4 GiB. The finding with the most leverage: Safari reach comes from wasm32, not from interpretation. A compiled wasm32 build of the same Lean code, not yet tried in Safari, was 27–217× faster than lean-vir in Chromium and Firefox, so it belongs in the benchmark too.

## LeanUI's own update loop runs 11–55× slower interpreted

The decisive test ran LeanUI's real framework code, not a proxy. A scratch copy of LeanUI moved to Lean 4.35 built unchanged. Its Bench app (`update`, `view`, diff and command encoding, with no DOM) was then packaged for lean-vir and timed against LeanUI's production wasm64 build. Command-word checksums were identical across native, wasm64 and lean-vir ([browser measurements §4](../research_notes/Lean%20vir%20backend%20for%20LeanUI/browser_measurements.md)). The ratios are the Lean-side cost of each js-framework-benchmark operation:

| Operation (Lean work only) | Chromium 141: lean-vir ÷ wasm64 | Release Firefox 158: lean-vir ÷ wasm64 |
|---|--:|--:|
| create 1,000 rows | **32×** | **55×** |
| replace 1,000 rows | 29× | 23× |
| update every 10th row | 16× | 11× |
| select row | 12× | 13× |
| swap rows | 31× | 23× |
| remove row | 11× | 14× |
| clear 1,000 rows | 20× | 24× |
| create 10,000 rows | **51×** | **49×** |

*CI machine, to be re-measured on the reference Mac. Medians of per-load medians, 3 loads × 10 samples (create 10,000: 3 × 3) ([browser measurements §4](../research_notes/Lean%20vir%20backend%20for%20LeanUI/browser_measurements.md)).*

On the reference Mac, LeanUI spends **about 3.8 ms of script** creating 1,000 rows in Chromium, and its keyed suite costs 1.19× hand-written JavaScript ([LeanUI BENCHMARKS.md](../docs/BENCHMARKS.md)). Applying the ratios above puts a lean-vir create-1,000 click at roughly **100–200 ms of script**. That is an upper bound, because the JS applier's share of the 3.8 ms would not be multiplied. On the CI machine, every operation except select-row in release Firefox already exceeded a 16 ms frame before any DOM work (CI machine, to be re-measured on the reference Mac). lean-vir would turn LeanUI from "close to vanilla JS" into a framework that drops frames on routine clicks.

Pixel work is worse, by another order of magnitude:

| Workload (same Lean source) | lean-vir ÷ compiled wasm32 | lean-vir ÷ LeanUI wasm64 |
|---|--:|--:|
| virtual-DOM build + diff, 1,000 rows | 27–30× | 9–22× |
| rows: strings, `mixHash`, `Std.HashMap` | 42–43× | 18–28× |
| `fib 27` | 117–178× | 85–167× |
| `ByteArray` lookup-table pass, 4 MB | 86–95× | 42–62× |
| `UInt32` 3-tap blur, 4 MB | 133–153× | 113–114× |
| `Float` per-byte gamma, 4 MB | 169–217× | 176–211× |

*Chromium 141 and release Firefox 158; CI machine, to be re-measured on the reference Mac. Full-output hashes matched native in every browser ([browser measurements §3](../research_notes/Lean%20vir%20backend%20for%20LeanUI/browser_measurements.md)).*

Today the editor's 19 image operations in Lean (wasm) take 0.61–0.73× the time of the same algorithms in plain JavaScript in Chromium (CI machine, to be re-measured on the reference Mac; [LeanUI BENCHMARKS.md](../docs/BENCHMARKS.md)). At 42–211× that becomes tens to hundreds of times slower than JavaScript, so the editor and the video lab are out of reach. The one workaround that needs no change to lean-vir, Lean fallbacks for missing byte-array primitives, made matters worse: the `ByteArray.uset` fallback ran in **quadratic time**, 3.3–4.3× slower for each doubling of input ([browser measurements §7](../research_notes/Lean%20vir%20backend%20for%20LeanUI/browser_measurements.md)).

The cause is structural. Lean's interpreter says it strives "for simplicity instead of performance". It calls every native primitive through "the 'boxed' versions of native functions" after a hash lookup by name ([lean4 ir_interpreter.cpp](https://github.com/leanprover/lean4/blob/master/src/library/ir_interpreter.cpp)). lean-vir builds it with `LEAN_DEFAULT_INTERPRETER_PREFER_NATIVE=false`, so `Init` and `Std` are interpreted too ([lean-vir build script](https://github.com/ejgallego/lean-vir/blob/main/scripts/build-upstream-probe.sh)). On wasm32, `lean_box_uint32` heap-allocates every boxed `UInt32` ([lean.h v4.35.0](https://github.com/leanprover/lean4/blob/v4.35.0/src/include/lean/lean.h)), and LeanUI's command encoder and pixel code are full of `UInt32`s. Going into the browser also hurt the interpreter more than compiled code: lean-vir ran **1.6–3.5× slower than the same interpreter natively** (CI machine, to be re-measured on the reference Mac), so host-only ratios understate the browser gap ([browser measurements §3](../research_notes/Lean%20vir%20backend%20for%20LeanUI/browser_measurements.md)).

The published figures agree once baselines are matched. The lean-vir author's own Node campaign put lean-vir **69–108× slower than a Lean → C → Emscripten module** on loop and array workloads, and at most about 10× slower where bignum arithmetic dominates ([FIR-UPDATE-20260929](https://github.com/ejgallego/lean-math-in-the-browser/blob/research/vir-fir-report/docs/FIR-UPDATE-20260929.md)). lean-vir's hosted benchmark catalog, run in Chromium on the CI machine (to be re-measured on the reference Mac), measured 18–320× against FIR's Emscripten route on lean-zip DEFLATE ([hosted catalog](https://ejgallego.github.io/lean-vir/benchmarks/); [browser measurements §3](../research_notes/Lean%20vir%20backend%20for%20LeanUI/browser_measurements.md)). A third-party report gives 110–160× against native code for loops and arrays (median 108× over all measurable cases) and 7–9× for bignum work ([lean-math-in-the-browser](https://github.com/joelcanary/lean-math-in-the-browser)). The often-quoted "usually 10x" was Henrik Böving's whole reply to "(10x? 100x?)", with no workload attached ([Zulip: what is lean.js](https://leanprover-community.github.io/archive/stream/113488-general/topic/what.20is.20lean.2Ejs.html)). Sebastian Ullrich's "20x is definitely possible AFAIR" dates from 2023 ([Zulip: precompilation](https://leanprover-community.github.io/archive/stream/270676-lean4/topic/Status.20of.20precompilation.html)). Apart from bignum work, interpretation came close to compiled speed only on tiny, boundary-dominated `prettyM` calls (about 1.1× total time, on the same hosted page and CI machine), which is the opposite of a UI update loop. Upstream interpreter work will help at the margin: #15493 is merged, and draft #15444 reports −32% wall-clock on an interpreted benchmark ([PR #15444](https://github.com/leanprover/lean4/pull/15444)). It will not change the order of magnitude.

## Bigger downloads and slower starts leave build simplicity and Safari as the gains

lean-vir does not shrink anything for an app of LeanUI's size. Its fixed runtime is **181 KB with brotli** (`runtime.wasm` 148,322 B plus `runtime.js` 32,327 B), which is more than the entire compiled Bench app. The Bench app's IR package adds 29 members, 662 KB raw and 84 KB brotli; `LeanUI.Diff` alone is 266 KB raw. The whole lean-vir LeanUI-ops site came to **266 KB brotli against 165 KB** for the wasm64 build of the same code ([browser measurements §6–7](../research_notes/Lean%20vir%20backend%20for%20LeanUI/browser_measurements.md); [lean-vir releases](https://github.com/ejgallego/lean-vir/releases)). IR compresses about 8:1, so the gap narrows only for very large apps or for a multi-app site that shares one cached runtime.

Startup slowed too. In Chromium, lean-vir was ready **about 2.4× later than compiled wasm32 and 1.8× later than wasm64**, and in release Firefox about 2× later than either. Its first useful result arrived **3–4× later**, because the first heavy call is also slow. The wasm compile is not the cost. Most of the time is JavaScript: `runtime.js` fetches resources, SHA-256-verifies every package member and parses packages before instantiation (CI machine, to be re-measured on the reference Mac; [browser measurements §5](../research_notes/Lean%20vir%20backend%20for%20LeanUI/browser_measurements.md)). Memory was a wash. lean-vir's wasm32 heap ended at 26.5 MiB against 24.3 MiB for compiled wasm32 and 42.7 MiB for LeanUI's pointer-heavier wasm64 build.

The first real gain is the build. A lean-vir app needs `@[vir_export]`, a resource library and one `needs` entry, after which "Lake … downloads the matching prebuilt interpreter" ([lean-vir README](https://github.com/ejgallego/lean-vir/blob/main/README.md)). In practice, packages regenerated in 2–8 seconds with no WASI SDK or npm ([browser measurements §1](../research_notes/Lean%20vir%20backend%20for%20LeanUI/browser_measurements.md)). Today LeanUI needs Docker, Emscripten, the QED64 runtime archives (about ten minutes cold) and a per-app C → wasm compile ([LeanUI TOOLCHAIN.md](../docs/TOOLCHAIN.md)).

The second gain is Safari. lean-vir's newest wasm feature is `extended-const` (Safari 17.4) ([features.json](https://github.com/WebAssembly/website/blob/main/features.json)). A third-party report ran it in current Chrome, Firefox and desktop Safari with 121 of 121 checksums matching ([REPORT.md](https://github.com/joelcanary/lean-math-in-the-browser/blob/main/docs/REPORT.md)). That would replace LeanUI's server-driven fallback, which costs a server session and about 1–2 ms per event round trip on localhost ([LeanUI DESIGN.md](../docs/DESIGN.md)).

Both gains come with friction that grows as apps grow. The extern catalog is an allowlist, and each group is admitted only after a measured wasm-size review ([NativeExterns.lean](https://github.com/ejgallego/lean-vir/blob/main/Vir/Compiler/NativeExterns.lean)). The core framework packaged only after `@[expose]` plus `vir_extern_fallback` was added for LeanUI's two inline-C buffer helpers, `pushU32` and `appendUtf8`. The editor was rejected for three inline-C pixel helpers and four missing catalog entries: `ByteArray.uset`, `ByteArray.usize`, `Float.toUInt8` and `Float.toInt64` ([browser measurements §7](../research_notes/Lean%20vir%20backend%20for%20LeanUI/browser_measurements.md)). Native C providers are possible, but "the resulting Wasm runtime is specific to that manifest" ([CLIENT_NATIVE_EXTERNS.md](https://github.com/ejgallego/lean-vir/blob/main/docs/reference/CLIENT_NATIVE_EXTERNS.md)). That brings back a per-app wasm build and loses the shared prebuilt runtime.

The Safari advantage also has a shelf life. Safari 27.0 shipped with JSC's `useWasmMemory64` off and "only supported in the IPInt tier", and the Safari 27.2 beta notes have no WebAssembly entries ([Safari 27 notes](https://developer.apple.com/documentation/safari-release-notes/safari-27-release-notes); [27.0 branch OptionsList.h](https://github.com/WebKit/WebKit/blob/safari-7625.1.29.18-branch/Source/JavaScriptCore/runtime/OptionsList.h); [27.2 beta notes](https://developer.apple.com/documentation/safari-release-notes/safari-27_2-release-notes)). But WebKit `main` now marks `WasmMemory64Enabled` as **stable and on by default** ([UnifiedWebPreferences.yaml](https://github.com/WebKit/WebKit/blob/main/Source/WTF/Scripts/Preferences/UnifiedWebPreferences.yaml)). The defensible reading (an inference; Apple has announced nothing) is that stable Safari gets Memory64 no earlier than a 2027 release, which would then likely run LeanUI's wasm64 build, possibly slowly at first. Older iOS devices will need a fallback for years, and the server-driven host already provides one.

## Upstream invests in the C backend, not the IR lean-vir consumes

No Lean interface is stable. `lean.h` changed by 202 lines from 4.34 to 4.35 and by 235 lines to 4.36.0-rc1, and `.olean` files are keyed to the exact build githash ([lean.h v4.36.0-rc1](https://github.com/leanprover/lean4/blob/v4.36.0-rc1/src/include/lean/lean.h); [upstream direction note](../research_notes/Lean%20vir%20backend%20for%20LeanUI/upstream_lean_direction.md)). Every approach therefore rebuilds against one exact toolchain each release. What differs is the layer each one depends on.

Compiled LeanUI depends on the C that Lean emits against `lean.h`. Since 4.30, that C emitter runs directly on the new LCNF pipeline ([PR #12781](https://github.com/leanprover/lean4/pull/12781)). It is the production path for every Lean binary, and the FRO's Year 4 roadmap commits to code-generator improvements: design now, "implementation at the beginning of 2027" ([FRO roadmap Y4-1](https://lean-lang.org/fro/roadmap/y4-1/)).

lean-vir depends on `Lean.IR`, which survives only as the interpreter's input ([LCNF/Main.lean v4.35.0](https://github.com/leanprover/lean4/blob/v4.35.0/src/Lean/Compiler/LCNF/Main.lean)), and that is the layer that is moving. 4.36.0-rc1 added `maxJp`/`maxVar` frame bounds to `DeclInfo` ([IR/Basic.lean v4.36.0-rc1](https://github.com/leanprover/lean4/blob/v4.36.0-rc1/src/Lean/Compiler/IR/Basic.lean)). A draft bytecode interpreter with a "remove IR" commit shrinks stored `.ir` by 38% ([PR #15557](https://github.com/leanprover/lean4/pull/15557)). It is a community draft with no maintainer review yet, but if it lands, lean-vir's design of extracting IR from compiled modules would likely need rework. To its credit, lean-vir absorbed the 4.36.0-rc1 change in six days without a wire-format bump, on a branch not yet merged (its CI also failed on October 20) ([feat/lean-436-rc1](https://github.com/ejgallego/lean-vir/tree/feat/lean-436-rc1)), and it has followed Lean releases within 1–10 days, apart from a 20-day lag on 4.30 ([claim verification Q4](../research_notes/Lean%20vir%20backend%20for%20LeanUI/claim_verification.md)).

Neither approach has upstream wasm support behind it. Lean dropped its wasm build in December 2024, so 4.15.0 was the last release with it ([PR #6424](https://github.com/leanprover/lean4/pull/6424)). Kim Morrison has since said "WASM is no longer supported" ([Zulip: wasm build](https://leanprover-community.github.io/archive/stream/270676-lean4/topic/wasm.20build.html)), and Markus Himmel called a return "a very high bar" ([Zulip: what is lean.js](https://leanprover-community.github.io/archive/stream/113488-general/topic/what.20is.20lean.2Ejs.html)). The FRO's browser direction is server-side ([lean4web](https://github.com/leanprover-community/lean4web)). Upstream does merge small platform fixes, including two from this project's own QED64 work ([#14864](https://github.com/leanprover/lean4/pull/14864), [#14886](https://github.com/leanprover/lean4/pull/14886)).

lean-vir adds project risk on top of that. It started on 2026-05-18. Its `main` branch has 348 commits, 342 of them by one FRO engineer working with AI agents, under Lean FRO copyright and Apache-2.0, on a personal GitHub account with 8 stars ([lean-vir commits](https://github.com/ejgallego/lean-vir/commits/main); [NOTICE](https://github.com/ejgallego/lean-vir/blob/main/NOTICE)). Its support statement "does not promise … compatibility across revisions", and it keeps "the current contracts without legacy APIs or backward compatibility layers" ([SUPPORT.md](https://github.com/ejgallego/lean-vir/blob/main/docs/SUPPORT.md)). The compatibility number went 2 → 3 → 6 → 7 between October 7 and 19 ([releases](https://github.com/ejgallego/lean-vir/releases)), and CI on `main` failed at `81de859` ([CI run](https://github.com/ejgallego/lean-vir/actions/runs/39403572375)). Two things soften this. lean-vir compiles Lean's interpreter and runtime unmodified, and LeanUI would use only its officially supported core (runtime, packaging, object API and minimal JS interop), not its experimental DOM and React layers. Even so, a framework built on lean-vir would inherit its churn release by release.

LeanUI's current path has its own durability debts, and they are worth paying down whatever is decided about lean-vir. It emits legacy exception handling (`-sWASM_LEGACY_EXCEPTIONS=1`) ([LeanUI TOOLCHAIN.md](../docs/TOOLCHAIN.md)), although standard exnref EH ships in Chrome 137, Firefox 131 and Safari 18.4 ([features.json](https://github.com/WebAssembly/website/blob/main/features.json)). It relies on Memory64, which stable Safari lacks, while capping memory at 4 GiB, so Memory64 currently buys no address space that wasm32 lacks. And it depends on the QED64 fork, whose per-release cost (330-commit merges, export regeneration, snapshot rebakes) comes from running the whole Lean frontend in the browser ([QED64 PATCHES.md](https://github.com/FawadHa1der/lean4/blob/qed64-wasm64/wasm64-build/PATCHES.md)). LeanUI uses none of that frontend. Building Lean 4.35's runtime, `Init` and `Std` for Emscripten wasm32 straight from upstream `stage0` took two small patches and five minutes in the measurement campaign, following the lean-fir recipe ([browser measurements §2](../research_notes/Lean%20vir%20backend%20for%20LeanUI/browser_measurements.md); [lean-fir setup-emscripten.sh](https://github.com/ejgallego/lean-fir/blob/167c2a4f9b15886888099c6cb902105c8ba72a27/integration/lcnf-c-wasm/setup-emscripten.sh)).

## lean-vir should stay wasm32-wasip1; Memory64 loses on every measured axis

A researcher built lean-vir five ways and ran every build that linked ([wasm64 port feasibility](../research_notes/Lean%20vir%20backend%20for%20LeanUI/wasm64_port_feasibility.md)). The routes compare as follows:

| Route | State in October 2026 | Measured or documented cost | Verdict |
|---|---|---|---|
| wasm32-wasip1, wasi-sdk clang, own JS loader (lean-vir today) | Builds from unmodified Lean v4.35.0 sources in about 5 minutes; runs in Chrome, Firefox, desktop Safari and Node | Baseline; 148 KB brotli | **Keep as the only target** |
| wasm32, Emscripten | Builds from the same sources; 720 KB stripped | 5–25% faster than the wasi-sdk build, but brings Emscripten's churn | Viable; no reason to switch |
| wasm64 (Memory64), Emscripten `-m64` | Prototype linked and ran under Node 24, Chromium and Firefox; 15 of 21 runtime tests passed | 1.09–1.36× slower, +10% raw size vs Emscripten wasm32 (+5% gzipped vs today's build), about 40% less recursion depth, no Safari or iOS, needs Node ≥ 24 | Only for heaps over about 4 GiB |
| wasm64, clang + WASI libc | Not possible today: wasi-sdk ships no wasm64 libc or libc++ and has "no plans" for p1; only an unofficial libc fork exists | n/a | Rule out |
| `MEMORY64=2` (wasm64 code lowered to a 32-bit memory) | Deprecated in Emscripten 6.0.13 (2026-10-19) | Ran at wasm32 speed in V8 | Do not adopt |
| WasmGC or direct wasm codegen | WasmGC has no reference counts; FIR is an internal, not-for-external-use workspace | n/a | Research only |

*Timings: CI machine, to be re-measured on the reference Mac.*

**Toolchain.** wasi-sdk says "There are no plans to add support for `wasm64-wasi{,-threads,p1,p1-threads}`". A `wasm64-wasip2` target waits on component-model#22, still open, where the May 2025 status was "no ETA while no one is working on this" ([wasi-sdk README](https://github.com/WebAssembly/wasi-sdk/blob/main/README.md); [component-model#22](https://github.com/WebAssembly/component-model/issues/22)). A wasm64 lean-vir is therefore Emscripten-only for the foreseeable future. Emscripten deprecated both `-sMEMORY64` (in favour of `-m64`) and the lowered `MEMORY64=2` mode during 2026 ([Emscripten ChangeLog](https://github.com/emscripten-core/emscripten/blob/main/ChangeLog.md)). WASI preview 1 is frozen, and lean-vir uses it only as a libc convention: its loader stubs the 13 WASI imports itself, so it is exposed to none of Emscripten's glue churn ([lean-vir factory-core.js](https://github.com/ejgallego/lean-vir/blob/main/web/src/runtime/factory-core.js)). That makes wasi-sdk plus its own loader the more durable toolchain for an interpreter that needs no threads or virtual file system.

**Porting effort.** The C side is almost width-clean. Two edits were needed: relaxing an explicit `#error "VIR resource payload encoding requires wasm32"` guard, and hiding lean-vir's `__cxa_throw` trap stubs from Emscripten's libc++abi ([resource_abi.cpp](https://github.com/ejgallego/lean-vir/blob/81de859a3ba1cb5da8bc5f128af025dd5a40b343/wasm/upstream_shim/abi/resource_abi.cpp)). Upstream Lean needed no patches, and the same `.irpkg` gave identical checksums on wasm32-wasip1, wasm32-Emscripten and wasm64-Emscripten. The real work is at the JS boundary. **67 of 85 exported functions switch to i64 (BigInt)**, 13 JS sites hard-code 4-byte pointers, and USize transport is wasm32-only by design. Worse, on LP64 a `lean_object*` handle can be a tagged scalar up to 2⁶³, so converting it to a JS Number silently drops bits; that bug caused the prototype's out-of-bounds trap. The prototype was 34 insertions and 18 deletions, plus a 19-line adapter. A production dual-width port is an estimated 300–800 lines ([wasm64 port feasibility §1, §3](../research_notes/Lean%20vir%20backend%20for%20LeanUI/wasm64_port_feasibility.md)). The maintainer has explicitly deferred it: "Keep the current wasm32 target guard… for a future wasm64 port" ([commit 8080b7a](https://github.com/ejgallego/lean-vir/commit/8080b7a)).

**Performance.** Under Memory64, the interpreter ran `fib(25)` **1.09–1.36× slower than lean-vir's shipped wasm32 build** across Node 24, Chromium 141 and Playwright's Firefox 142. The lowered `MEMORY64=2` build, which has the same 8-byte pointers on a 32-bit memory, ran at wasm32 speed in V8. So in V8 the cost comes from the 64-bit memory itself, not from fatter objects (in Firefox the lowered build was slower still). Turning off V8's Memory64 trap handling made no measurable difference (CI machine, to be re-measured on the reference Mac; [wasm64 port feasibility §4](../research_notes/Lean%20vir%20backend%20for%20LeanUI/wasm64_port_feasibility.md)). This matches SpiderMonkey's 10% to over 100% range and its advice that "the only reason to use Memory64 is if you actually need more than 4GB of memory" ([SpiderMonkey blog](https://spidermonkey.dev/blog/2025/01/15/is-memory64-actually-worth-using.html)). The main interpreter benefit of wasm64 is unboxed `UInt32`, and it is narrow: kernels that need it are 42–211× too slow interpreted anyway.

**The "upstream tests only 64-bit" argument does not apply to lean-vir.** That argument is right for running the whole Lean frontend in a browser, which loads `.olean` files whose header stores `size_t base_addr` ([module.cpp v4.35.0](https://github.com/leanprover/lean4/blob/v4.35.0/src/library/module.cpp)). That is why QED64 is LP64 and why cauli's wasm32 fork still builds an i386 stage. lean-vir loads no oleans in the browser. Its packager runs as a native 64-bit program over the host's ordinary module data and writes width-independent `.irpkg` files ([CachedImports.lean](https://github.com/ejgallego/lean-vir/blob/81de859a3ba1cb5da8bc5f128af025dd5a40b343/Vir/Compiler/CachedImports.lean)). Upstream's code generator also checks `USize` constant folds in both the 32-bit and 64-bit worlds ([#13974](https://github.com/leanprover/lean4/pull/13974), [#15277](https://github.com/leanprover/lean4/pull/15277)).

The residual wasm32 risk is real but small. 32-bit is untested upstream, and one width bug has already slipped in. `LEAN_SCALAR_PTR_LITERAL`, added with static initializers in January 2026, picks its 32-bit layout only `#ifdef LEAN_EMSCRIPTEN` ([PR #12082](https://github.com/leanprover/lean4/pull/12082); [lean.h v4.35.0](https://github.com/leanprover/lean4/blob/v4.35.0/src/include/lean/lean.h)). On wasm32-wasip1 it truncates static `Name` hashes. A wasi-sdk test read `0x0000000044332211` instead of `0x8877665544332211`. No affected literal appears to be linked into today's lean-vir binary, so the bug looks latent ([wasm64 port feasibility §1](../research_notes/Lean%20vir%20backend%20for%20LeanUI/wasm64_port_feasibility.md)). The fix is QED64's patch 0003: gate the macro on `UINTPTR_MAX` instead. Reporting it to lean-vir and upstream is cheap and protects every wasm32 route.

**Hybrids.** lean-vir is already a hybrid: the runtime, a stage0 C subset and its extern catalog are native, and only the reachable IR closure (the app plus the `Init` and `Std` code it uses) is interpreted. A single module that embeds the interpreter inside LeanUI's wasm64 app is feasible, because lean-vir's shims link under `em++ -m64` with zero unresolved symbols. But LeanUI's archives contain no interpreter, the result would be tied to lean-vir's exact Lean githash, and it would inherit both the Memory64 slowdown and the BigInt-handle work. If an interpreter is ever wanted inside LeanUI, two separate modules exchanging bytes is the durable shape ([wasm64 port feasibility §2, §6](../research_notes/Lean%20vir%20backend%20for%20LeanUI/wasm64_port_feasibility.md)).

None of the faster-interpreter options closes a 10–200× gap. Partial evaluation à la weval gave 1.8–2.9× on other interpreters ([Fallin & Bernstein](https://arxiv.org/html/2411.10559v1)). WasmGC exposes no reference counts, so a Lean backend on it would lose the RC = 1 in-place updates that make Lean's array and pixel code viable ([Counting Immutable Beans](https://arxiv.org/abs/1908.05647)). The FRO engineer's own direct-to-wasm backend, FIR, is an "internal, non-official research workspace — not for external use" ([lean-fir](https://github.com/ejgallego/lean-fir)). In its author's tables, the Lean → C → Emscripten route beats FIR on every workload except one ([FIR-UPDATE-20260929](https://github.com/ejgallego/lean-math-in-the-browser/blob/research/vir-fir-report/docs/FIR-UPDATE-20260929.md)).

Wasm64 becomes the right choice for lean-vir only when four conditions hold together: a real LeanUI workload needs more than about 3–4 GiB of Lean heap in one instance, stable Safari and iOS ship Memory64, measured Memory64 overhead in the target engines falls to about 10% or less, and the project is already on Emscripten. Only the last holds today. Until then, the near-zero-cost hedge is to upstream lean-vir's width-neutral pieces: the literal fix, pointer-width-aware array helpers and a scalar-aware handle accessor. A later wasm64 decision would then be mostly a build-flag change.

## A four-way benchmark answers the open questions for days, not weeks, of work

Adding lean-vir as an implementation is worth doing, and it fits LeanUI's harness cleanly. The harness drives apps only through the DOM and `window.__leanui`. The mounts, page list and startup file list in `bench.mjs` are hard-coded per implementation, and the memory probe reads `stats.heapBytes` ([bench.mjs](../tests/browser/bench.mjs)). Small, contained changes cover it: a `--leanvir-dir` mount; an `.mjs` MIME type, because lean-vir's runtime is an ES module; startup file lists per implementation; a `VirTransport` in `leanui.js` that sets `heapBytes` from `exports.memory.buffer.byteLength` and reuses the server host's `applyEncoded` path; ratio columns for every implementation; and, for the release-browser and Safari runs, extending `bench/runner.html`, `selfbench.mjs` and `tools/bench-tables.mjs` to N implementations. For the editor benchmark, `wasmBytes()` must ask the transport, and runs must start at small image sizes with a long slow-op limit ([editor-bench.mjs](../tests/browser/editor-bench.mjs); [integration note §4](../research_notes/Lean%20vir%20backend%20for%20LeanUI/leanui_integration_benchmarks.md)).

The framework side is already proven in a scratch copy: `@[expose]` and `vir_extern_fallback` on `pushU32` and `appendUtf8`, a Lean host that collects flushes in an `IO.Ref`, and per-app entry modules exporting `start`/`event`/`drain` ([browser measurements §7](../research_notes/Lean%20vir%20backend%20for%20LeanUI/browser_measurements.md)). Keep lean-vir imports in their own `lean_lib` so the core library stays `Init`/`Std`-only.

Two operational rules matter more than the code. First, pin an exact lean-vir commit together with its runtime resource. Its contract changes weekly, and mixing JS and wasm from different revisions "has undefined behavior" ([JS_API.md](https://github.com/ejgallego/lean-vir/blob/main/docs/guides/JS_API.md)). Second, align Lean versions. lean-vir `main` is on 4.35 and LeanUI's fork on 4.34. Either pin lean-vir's 4.34-era runtime resource from October 7 ([releases](https://github.com/ejgallego/lean-vir/releases)), not yet checked against the APIs used at `81de859`, or move LeanUI to 4.35. The core already builds unchanged on 4.35, but the editor's inline C must replace `lean_copy_byte_array`.

Two more implementations make the benchmark decisive rather than merely descriptive.

**A compiled wasm32 build of the same apps.** It separates "what interpretation costs" from "what wasm64 and the QED64 archives cost". The measurements contain an unexplained gap. LeanUI's wasm64 build was 1.06–3.4× slower than compiled wasm32 in Chromium on the six workloads, and 0.8–2.1× in release Firefox (CI machine, to be re-measured on the reference Mac; [browser measurements §3](../research_notes/Lean%20vir%20backend%20for%20LeanUI/browser_measurements.md)). Memory64 alone costs only 1.07–1.14× on a C workload ([LeanUI BENCHMARKS.md](../docs/BENCHMARKS.md)). The two builds also differ in Lean version (4.34 vs 4.35) and runtime source (QED64 vs upstream stage0), so the extra cost has not been attributed. A compiled wasm32 build is also the obvious candidate for in-page Safari at compiled speed. That remains an inference: it has not yet been run in Safari, though its legacy EH works in Safari 15.2+ ([features.json](https://github.com/WebAssembly/website/blob/main/features.json)).

**A native-interpreter baseline** (`lean --run -Dinterpreter.prefer_native=false`). It separates "interpretation" from "interpretation inside wasm".

To match the preference for simple designs, keep the scope small. Port Counter and Bench first; the integration note estimates the Counter proof of concept at 2–4 days. Add TodoMVC and Site next, for Safari correctness. Port the editor and video lab only if lean-vir's catalog gains `uset`, `usize`, `Float.toUInt8` and `Float.toInt64`. Full parity is an estimated 3–6 weeks and is not worth it on these numbers ([integration note §5](../research_notes/Lean%20vir%20backend%20for%20LeanUI/leanui_integration_benchmarks.md)). Measure per-operation CPU split into Lean time (lean-vir's `callTimed`) and applier time, startup phases, download size and memory. Re-measure view-nesting depth with `depth.mjs`, since interpreted frames are larger, and add a call-cost probe and a `UInt32`-heavy kernel to capture wasm32 boxing. Run all of it on the reference Mac in Chrome, Firefox and Safari. Every browser ratio measured for this report is a hypothesis from a loaded cloud VM until then.

## Conclusion

"Interpreter or compiler" turns out to be two separate choices: execution strategy and pointer width. Speed comes from compiling, and the measured gap is one to two orders of magnitude. Browser reach comes from wasm32, which every engine runs today. lean-vir pairs reach with interpretation, and LeanUI pairs speed with Memory64. Compiled wasm32, the combination neither project ships, was the fastest browser build in 11 of the 12 workload–browser pairs measured (CI machine, to be re-measured on the reference Mac). It can be built from upstream sources without the full-frontend fork. If the Mac and Safari runs confirm this, it could retire the Memory64 requirement and the Safari server fallback for in-page use, and the QED64 dependency could go with them. That would make it the simplest and most durable configuration available to LeanUI, and the benchmark should be designed to confirm or refute it.

lean-vir's role for LeanUI is that of a well-maintained reference point, not a foundation. It tracks the FRO's interpreter work, so re-running it costs little each time upstream lands interpreter speedups. It also leaves room for a later niche such as a no-toolchain development loop or user scripting inside an app. The cheapest durable moves now are to pin it in the benchmarks and to upstream the width fixes that keep every wasm route open. Committing LeanUI's runtime to a fast-moving proof of concept would be the least durable choice.

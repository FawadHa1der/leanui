Verified threads, side by side JavaScript next to iris-lean-proved kernels

Each scenario runs the same multithreaded job several ways in Web Workers: hand-written JavaScript, and kernels proved in iris-lean, translated to JavaScript. The proofs cover safety under sequentially consistent interleavings, not speed, progress or the JavaScript around a kernel.

verified: proved in iris-lean, translated hand-written JavaScript ✗ broken on purpose: what went wrong, instead of a speed

The hand-written lanes are broken on purpose, idiomatic, or the same algorithm by hand; the verified ones are translated from the very Lean constants the theorems are about, into JavaScript over one SharedArrayBuffer. Open a lane for its proof chip: what is proved, what is trusted, and what is not proved.

Speeds are operations per microsecond, all threads together, measured in this browser on this machine: read them as ratios between the lanes of one run. A lane runs alone, so lanes do not compete for the cores. The live views read shared memory once per frame; the only addition to a lane is one Atomics.or per claimed tile in S5's two claiming lanes, which records who drew it. A page cannot see CPU time; the Node harness (node iris/bench/harness.mjs) reports CPU time per operation and also runs the native and wasm32 lanes. Broken lanes show correctness counts only. Fuzz mode adds random delays before shared-memory operations: more interleavings, not a fair speed comparison (the charts show the runs without it; Details has both). iris/README.md in the repository has the details, the coverage of every JavaScript threading mechanism, and the trusted base.
